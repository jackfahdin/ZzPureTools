# CI 与性能门禁复核 · 2026-10-12

## 结论与范围

CI 兼容性修复和“正式报告 + 绝对预算 + 同环境相对比较”的门禁方向可行，
但当前状态不能标记为性能门禁全绿。本次修复了采集启动循环、导航树隐藏投影开销、
滚轮弹出尺寸重复计算和截图版本混用；保留历史性能档案、参考 JSON 与门限不变。

审查范围为 `6a49d3a..0c455de` 的 27 个提交，以及本轮修复；重点检查
CI / Preset / CTest 接线、编译兼容性、报告完整性、环境身份、运行时行为与截图。
公开类型命名调整属于此前有意进行的 API 清理，旧调用方仍需同步名称。

### 尚未通过的性能条件

1. **径向仪表动画帧间隔。** 当前环境下 P95 仍略超 16.7 ms。
   该指标记录相邻 Paint 事件开始时间，包含 Qt 动画调度、事件循环和绘制间隔，
   不是单次 `paintEvent()` 的耗时。尚不能把轻微超限归因于某一段绘制代码，
   也不能因接近门限就算通过。后续应在受控参考环境定位调度与绘制开销。
2. **四份正式参考报告缺失。** `workspace-components`、`fluent-standard-surfaces`、
   `backdrop`、`radial-gauge-animation` 已声明门限但尚未建立对应参考报告，
   `platform.performance-threshold-contract` 正确失败关闭。
3. **旧、新环境不能做相对比较。** 用本轮导航报告执行真实比较器，得到
   `INVALID navigation-pane environment;gpu`，明确拒绝 Mesa 26.0.3 与 26.0.8 混比。
   按负责人选择保留历史基线，相对门禁标记为待复核。

要恢复正式门禁，需要回到匹配的原参考环境补采缺失报告并执行三轮比较，
或另行决定完整迁移参考环境、审核全部新报告。不能只补四个新环境报告到旧的十二份中。

### 后续定位与门禁自测修复

继续定位时发现：原 `platform.performance-threshold-contract` 先检查正式参考完整性，
缺四份报告会提前退出，后面的比较器、环境不匹配拒绝、噪声分析和工作区证据自测未执行。
`9084745` 将两类职责拆开：旧测试名继续检查真实参考并保持失败；新增
`platform.performance-comparison-contract` 独立运行真实比较器与校验器的正反例。
采集脚本仍只排除旧的完整性检查，新自测会正常执行。缺失诊断现在列出具体场景。

动画方面，GLib/UNIX 对照未消除仪表超限；纯 Qt、跳过 Paint 和刻度批量绘制实验见
[隔离诊断证据](evidence/animation-isolation/2026-10-12/)。批量绘制没有稳定收益，
已撤回并重建原始控件库。最终原程序复验：开关 P95 16.585656 ms，本轮通过；
仪表 16.725868 ms，仍超 16.7 ms。开关本轮通过不覆盖此前失败。
本次修复让门禁自身的测试真正执行，没有修改历史参考、预算或 `frame-time` 语义。

## Qt 定时等待精度与诊断环境隔离

在未修改 SDK 的前提下，重新构建独立 UNIX 分发器诊断库，解决此前仅替换
`timerWait()` 未实际生效的问题。八次原始基准运行均记录替换函数入口标记，
同一 UNIX/共享内存配置按取整 / 精确 / 精确 / 取整执行：仪表 P95 分别为
16.740077、16.237982、16.220062、16.722756 ms；开关四轮均低于 16.7 ms。
这验证了 `timerWait()` 毫秒向上取整对 UNIX 路径帧间隔的影响，仍有约 19–20 ms
的最大间隔，不能声称抖动已消除。原始报告、入口日志、数值校验日志与复现命令见
[Qt 定时精度证据](evidence/qt-timer-precision/2026-10-12/README.md)。

候选 Qt 补丁保留纳秒等待，并在 WebAssembly 的两个毫秒消费者处显式向上取整。
五个定时列表检查在原 SDK 上两项精度检查失败，候选实现五项通过；补丁通过
`git apply --check`。只编译运行了 Linux UNIX 诊断库，未应用到安装 SDK，
未构建验证 WASM/CoreFoundation。默认 GLib 消费端仍有毫秒取整，本轮没有重新
运行默认正式基准，上节的正式失败结论不变；候选诊断报告不提升为历史参考。

`1cf79f1` 修复三个正式脚本入口可能继承诊断环境参数的问题：拒绝非空
`QT_NO_GLIB` / `LD_PRELOAD` 以及任何已设置的 `QT_XCB_NO_MITSHM`。
报告指纹未包含这些开关，必须在构建/采样前阻止混用，而不是产生可被误比较的报告。
新增契约覆盖 24 个入口组合，旧代码先失败、修复后通过；连同既有比较器、采集、
runner、脚本契约和两项架构审计，7 项 CTest 通过。独立审查未发现阻断问题。

下一步是评估默认 GLib 的高精度等待方案或独立审核 UNIX 性能配置；
不向生产框架引入私有 Qt 注入，不改变现有预算及正式环境定义。

## 默认 GLib 路径的候选修复验证

`23c0abf` 将 Qt 剩余纳秒等待通过 GLib `ready_time` 微秒截止时间接口传递，
保持 GLib 后端。普通和空闲源各自缓存绝对目标，禁用、无待激活定时器、优先级
让出及 dispatch 时清除。独立审查发现首次候选反复设置截止时间会自唤醒，
实测 30 ms 内 27850 次 poll；补充真实 poll 计数后修复为 3 次，原实现 2 次。
首次候选的性能采样废弃，不计入结论。

修正后原程序串行 ABBA：仪表原实现 P95 16.753429 / 16.764049 ms，
候选 16.229435 / 16.225988 ms；开关候选 16.410104 / 16.459490 ms。
八次基准的进程 CPU 占用均约 1%，诊断库入口标记全部确认生效。
候选 15 项定时源检查通过，原版/候选各 9 项事件循环检查通过；原版微秒
截止时间检查保留失败，不把独立 CTest 描述为全绿。默认等待系统调用追踪确认
`ppoll` 接收到非整毫秒超时；性能测量期间未启用追踪或自定义 poll。

恢复未修改的 SDK 后，6 项定向正式测试 4 项通过、2 项失败：仪表
P95 **16.759788 ms** 仍超限，开关 **16.622811 ms** 本轮通过，四份参考仍缺失。
当前框架 7 项相关契约和审计通过；历史基线、16.7 ms 门限及采样语义未改变。
原始数据、CPU 记录、测试日志、补丁及复现步骤见
[GLib 修复验证](evidence/qt-glib-precision/2026-10-12/README.md)。

这解决了 GLib 候选实现的精度问题，但未替换正式 Qt SDK。候选依赖 GLib ≥ 2.36，

## 可复现命令

在已经配置并构建的本机诊断目录中，使用真实环境身份运行：

```bash
export QT_QPA_PLATFORM=xcb
export ZZ_BENCHMARK_COMMIT=$(git rev-parse HEAD)
export ZZ_RUNNER_IMAGE_DIGEST="sha256:$(sha256sum docs/performance/evidence/ci-review/2026-10-12/environment.json | awk '{print $1}')"
export ZZ_GPU_IDENTITY='Mesa llvmpipe LLVM 21.1.8 Mesa 26.0.8 Xvfb 1920x1080x24'
taskset -c 8 xvfb-run -a -s '-screen 0 1920x1080x24 -nolisten tcp' \
  taskset -c 10 ctest --preset linux-gcc-benchmarks \
  -L benchmark --output-on-failure -j1
```

此命令只适用于表中这台诊断环境，不是跨机器通用的身份配置。
正式参考采集应在匹配环境中使用
`scripts/ci/capture-linux-performance-reference.sh`；脚本仍会拒绝绝对门限失败和环境混用。
